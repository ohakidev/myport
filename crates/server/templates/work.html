Myport / Rust / Axum / WebAssembly

Can someone read the work before entering the 3D scene?

A Rust portfolio with server-rendered / and /work routes and an optional Rust/WebAssembly playground.

Rust server source Rust playground source Earlier Next.js commit

Problem

Make the portfolio readable without requiring a visitor to load the interactive 3D scene first.

Implementation

Axum + Askama render / and /work from server-side HTML. /play is a separate entry point backed by Rust and WebAssembly.

Key decision

Keep the GitHub refresh off the page request path. Pages read a RwLock<Portfolio> snapshot, so page requests do not wait on GitHub and home keeps its saved list when refresh fails.

Refresh policy, runtime requirements, and historical Next.js details

A background HTTPS refresh has a four-second timeout and one-hour interval. Failures or empty results keep the last readable snapshot. The seed keeps the portfolio readable before a successful refresh, but may become stale during an outage.

The crates/play crate has a wasm32 entry point and WebGL 2 renderer. Browser storage keeps session and preference data with legacy-session handling. The separate playground still requires its compiled WebAssembly asset at startup and WebGL 2 to render.

This earlier Next.js commit predates the current Rust migration. Its root route passes GitHub data to Journey, which owns selection state around the Three.js GameWorld and ProjectPanel.

Activity registration / Next.js / MongoDB

How does a form response become attendance?

Review scope: one pinned Next.js and MongoDB snapshot, following PublishForm, SubmitForm, and joinActivity. This documents code paths, not deployed behavior.

Pinned activity commit PublishForm SubmitForm joinActivity

Problem

A submitted form, a booking, and attendance are separate states. Following only the form response hides the checks between them.

Implementation

PublishForm saves activity and registration windows after checking for a session. SubmitForm saves a response, updates the submission count, then records a booking when one is absent.

Key decision

Treat check-in as its own gated transition. joinActivity requires a booking, an open registration window, and client-reported coordinates within 100 metres of the saved location. That proves reported proximity, not physical presence.

Review authorization, partial failure, and supporting sources

Trust boundaries and partial failure

In the pinned commit, PublishForm checks for a session but does not call the admin-role guard used by other actions. joinActivity receives coordinates from the client, so its distance check validates reported proximity, not physical presence.

SubmitForm saves the response, updated form, and optional booking in ordered writes without a transaction. A later failure can leave an earlier write persisted. These are source-review observations, not production incident evidence.
